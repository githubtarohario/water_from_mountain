第 14 章

粒子の描画 — インスタンシングとスフィア・インポスター

12,000 個の球をどう効率よく描くか。この章では、1 回の描画命令で大量の同じ形を描くインスタンシングと、平らな四角形をピクセルシェーダーで「本物の球」に見せるスフィア・インポスターの技法を学びます。

14.1 課題 — 球を 12,000 個描く

球を三角形メッシュで作ると、粗くても 1 個 100 三角形ほど必要で、12,000 個で 120 万三角形になります。しかも遠くの粒子は数ピクセルにしか映らず、ほとんどが無駄になります。そこで「カメラに正対する四角形を描き、ピクセルシェーダーで球の形に削る」スフィア・インポスター（impostor = 替え玉）を使います。1 粒子 2 三角形で済み、どんな距離でも輪郭が滑らかです。

第 15 章

表面生成 — スクリーンスペース流体レンダリング

粒子の集まりを「1 枚の水面」として見せるには、粒子の間を滑らかにつなぐ面が必要です。この章では、3D のメッシュを作らずに画面空間だけで水面を作る手法（van der Laan ら 2009）を、深度パス・ぼかしパス・合成パスの順に学びます。

15.1 2 つのアプローチ

  • 陽なメッシュ生成: 粒子から密度場を作り、Marching Cubes で等値面のメッシュを抽出する。視点によらない正確な面が得られるが、毎フレーム 3D 格子を走査するため重い。
  • スクリーンスペース法: 粒子を球として深度だけ描き、画面上でぼかして法線を復元する。画面のピクセル数にしか依存せず軽い。見える面しか作らないが、リアルタイム表示には十分。
図 15-1 スクリーンスペース流体レンダリングの 3 パス

15.2 深度パス

第 14 章の球インポスターを使い、色の代わりにビュー空間の z を R32_FLOAT テクスチャに書きます。メインの深度バッファ（地形描画済み）と組で描くので、地形の後ろの粒子は自動的に消えます。テクスチャは 0 でクリアし「0 = 流体なし」とします。表面用の球半径は粒子間隔の 1.3 倍にして、隣の球と重なり隙間を作らないようにします。

15.3 バイラテラルぼかし

深度テクスチャをそのままぼかすと、流体の輪郭で背景（深度 0）と混ざって縮み、また流体同士が重なる段差も溶けてしまいます。バイラテラルフィルタは「距離が近く、かつ値も近い」画素だけを平均するフィルタで、輪郭を保ったまま内部を滑らかにできます。

wk = exp(−k2 / 2σs2) · exp(−(dk − d0)2 / 2σd2),   d′ = Σ wk dk / Σ wk
{{SVG_BILATERAL}}

実装上の工夫が 3 つあります。

  • 透視補正: ぼかし半径をワールド単位（0.9 m）で決め、それを画面に投影したピクセル数を使う。近い流体は広く、遠い流体は狭くぼかされ、距離によらず同じ滑らかさになる。
  • 流体外の除外: 深度 0 の画素は重みに入れない。これで輪郭が内側に縮まない。
  • 分離可能: 2D のフィルタ（R2 タップ）を横 1D + 縦 1D（2R タップ）に分ける。厳密には等価でないが十分近く、はるかに速い。横→縦を 4 回反復する。
{{CODE:shaders/FluidSurface.hlsl:float PSBlur(FullscreenVSOut i) : SV_Target:}}
σd の決め方 最初は 0.35 m にしていましたが、球の凹凸（≈ 0.4 m）が平滑化されず「ブロック状」に見えました。流体外は別途除外しているので、σd は球の凹凸より十分大きい 1.5 m にしてよく、それで滑らかな面になりました。「何と何を区別したいのか」を考えて閾値を決めるのがコツです。

15.4 法線の復元

ぼかした深度から、各ピクセルのビュー空間位置を復元します。第 1 章の透視投影の式を逆向きに使います。

p = (ndcx · d / P00,  ndcy · d / P11,  d)

隣接ピクセルとの位置の差（偏微分）の外積が法線です。輪郭では深度が飛ぶので、左右・上下それぞれで「差の小さい側」を採用して法線が壊れないようにします。ピクセルの +y は画面の下向き（ビュー空間の −y）なので、(+x) × (−y) = −z がカメラ側を向く法線になります。

第 16 章

これまでの部品を 1 つのアプリケーションにまとめる「骨組み」を学びます。Windows のウィンドウとメッセージ、入力の受け取り、時間の管理、そして物理と描画を毎フレーム呼ぶループの構造です。

16.1 ウィンドウとメッセージループ

Windows のアプリケーションは、OS から送られる「メッセージ」（キー入力、マウス移動、サイズ変更…）をウィンドウプロシージャで処理します。ゲームやシミュレーションでは、メッセージが無いときにも描画を続けたいので、PeekMessage で「メッセージがあれば処理、無ければ 1 フレーム描画」という形にします。

  • 物理更新は dt に応じてサブステップ数が決まり（第 10 章）、描画は 1 回です。

動くものを「速く」「壊れにくく」するための実践的な知識をまとめます。このプログラムの開発過程で実際に起きた問題と、その解決を例にします。

17.2 ボトルネックの見つけ方

  • CPU か GPU か: 粒子モードと表面モードで FPS が違えば、その差は GPU。物理を一時停止（Space）して FPS が跳ね上がれば CPU（物理）がボトルネック。
  • 計測を入れる: steady_clock で各段（格子構築 / 密度 / 力 / 積分 / 描画）の時間を測り、タイトルに出す。推測より計測。
  • スケーリングを見る: 粒子数を 2 倍にして時間が 2 倍なら線形、4 倍なら O(N²) の部分が残っている。

17.4 描画のデバッグ

  • 何も映らない: カリングを無効に → 映れば巻き順。それでも映らなければ行列（転置忘れ、near/far）やビューポート。
  • D3D デバッグレイヤー: Debug ビルドで有効化。SRV と RTV の同時バインド、未設定のステート、入力レイアウトの不一致などを出力ウィンドウに警告する。
  • 中間結果を見る: 法線を色として出す、深度テクスチャをそのまま表示する、ぼかし回数を 0 にする。パスを 1 つずつ確かめる。
  • シェーダーのコンパイルエラー: メッセージボックスに行番号つきで出る。HLSL は暗黙の型変換に厳しい（int2 と float2 の混在など）。
コラム: 「最初は動かない」が普通 このプログラムの初回実行では、min/max マクロとの衝突でコンパイルが通らず、次に粒子が谷の外に飛散し、表面生成はブロック状でした。1 つずつ原因を切り分け、パラメータの意味を考えて直すことで完成しています。CG と物理シミュレーションの開発は、この「観察 → 仮説 → 修正」の繰り返しです。

ai = [ Σj m(pi+pj)/(2ρj) · 45/(πh6)(h−r)2 r̂ij + μ Σj m(vj−vi)/ρj · 45/(πh6)(h−r) ] / ρi + g
